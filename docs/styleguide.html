  • Purpose of This Style Guide

    This style provides a common, shared set of (lightweight) guidelines for anyone who wishes to contribute source code and/or scripts to the UOX3 project, in order to help ensure that those contributions follow a standardized approach not only for code style, but also for conventions and practices used in the project. This also improves the maintainability of the project in the future.

    The UOX3 code base has historically been a hodgepodge of different styles and approaches, written by people with varying programming skills over a period of more than 20 years, and that history highlights the need for a standard that can be followed when working on the project.

    These guidelines are not meant to be understood as hard requirements, yet the closer to the guidelines that new contributions adhere to, the easier it will be to review any changes in context of the current code base and - if accepted - merge those contributions in.

  • Basic Style Guide

  • General Guidelines

    Above all else, please take to heart the general guidelines listed below and follow them as best you can:

    • Write understandable, self-documenting code - Give sensible, descriptive names to classes, functions and variables that clarify their purpose, rather than short and ambiguous names that say nothing about what they are for.
    • Add comments where needed - Use comments to leave hints for the reader of your code if the code is not self-explanatory for the average programmer. If the code you write is so advanced and complex that no one else can understand it by reading it, then comments are crucial for anyone else to be able to maintain it if/once you've lost interest in the project and moved on (as happens).
    • Be consistent with existing code - Make life easy for anyone who needs to read or maintain your code in the future, by adopting the coding style, conventions and practices most commonly used in the project. If the existing code offers two alternatives on how to proceed in this context, choose one of the two; don't introduce a third option.
    • Avoid making unnecessary, sweeping style changes - If possible, avoid making sweeping changes throughout the entire code base that forces everyone else to adopt your own preferred style. Not only is it quite an assumption to make that everyone else on the project will prefer your style, it may also cause problems for anyone who wishes to merge their code changes with yours; instead of comparing differences in a few functions in a few files, they now potentially have thousands of differences to go through!
    • If unsure, ask - If you're unsure if a change would conflict with the guidelines laid out in this Style Guide, don't hesitate to bring it up in Discord or on the UOX3 Community forums to get a second opinion - preferably before you make the change!

    If you have identified a need for a change that conflicts with the above points, or with anything else in this Style Guide, create a new topic on the Communtiy Forums and state your case, or bring it up in the Discord chat. None of these "rules" are etched in stone, they can (and should) be challenged, updated and added to when appropriate.

  • C++ Target Version & Compilers

    All new code written for UOX3 targets C++17 (compiled with /std:c++17 on MSVC or -std=c++17 on GCC/Clang), and aims to be cross-platform conforming across 64-bit Windows, Linux, and macOS platforms when built using Visual Studio 2022 (MSVC / ClangCL), GCC 11+, Clang 15+, and/or CMake 3.18+.

    • C++17 Cheatsheet
    • C++14 Cheatsheet
    • C++11 Cheatsheet
  • Cross-Platform Support

    UOX3 aims to be cross-platform conformant across (at least) 64-bit Windows, Linux and macOS platforms, with feature parity between each platform. Implementations specific to any one particular platform should be avoided if possible, though there might be exceptions for special cases where platform-specific handling is unavoidable - such as when dealing with console and/or networking.

    Any code being contributed that does not compile, run and function the same on all the above-mentioned platforms will probably not be approved for inclusion in UOX3 until/unless necessary changes have been made to comply with the above.

  • Naming Conventions

    Use Self-Descriptive Names

    Always prefer self-descriptive names (skillUsageDelay instead of skUseDel, itemCount instead of ic)

    Filenames

    If creation of new source files is necessary, use camelCase when naming the files to make the name more readable in a list of other, perhaps similarly named files. Try to stick close to existing naming practice.

    Classes/Methods/Functions

    Use PascalCase for class/function/method names.

    Variables and Parameters

    Use camelCase for variables, non-method class/struct members and function/method parameters.

  • Advanced Style Guide

  • Auto keyword
    • Use the auto keyword when declaring variables to automatically deduct the variable type based on the initializer. Same can be done with return types for functions. Examples:
      • // Using auto with a variable
auto myChar = "Hello"; // type is const char* pointer to const char[5] array
auto myString = "Hello, World!"s; // type is std::string (note the 's' at the end)
auto myVar = GetMyVarValue(); // type depends on what GetMyVarValue() returns

// Using auto with functions
auto CItem::SetRegion( UI16 newValue ) -> void
{
	regionNum = newValue;
	UpdateRegion();
}
auto CItem::GetRegionNum( void ) const -> UI16
{
	return regionNum;
}
  • C++ Language Features & Conventions

    Core Language Conventions (C++11 to C++17)

    • nullptr: Always use nullptr instead of 0 or NULL for pointer initialization and comparisons.
    • constexpr: Prefer constexpr for compile-time constants and array bounds instead of #define macros:
      • constexpr UI16 CREATE_MENU_OFFSET = 5000;
constexpr SI08 MAX_Z_STEP = 15;
    • Scoped Enums: Use enum class or strongly-typed enums for state flags, object types, and paperdoll layers (e.g. ItemLayers, TileFlags, ObjectType).
    • Structured Bindings: Use structured bindings to unpack pairs, tuples, or coordinate structs cleanly:
      • // Unpacking pairs returned from functions
auto [mapWidth, mapHeight] = Map->SizeOfMap( worldNum );

// Clean iteration over std::map / std::unordered_map
for( const auto &[serial, obj] : ObjectFactory::get().allObjects )
{
	if( ValidateObject( obj ))
	{
		...
	}
}

    Standard Attributes

    • [[maybe_unused]]: Cleanly suppresses compiler warnings on intentionally unused parameters or variables:
      • [[maybe_unused]] UI16 ignoreMe = 0;
    • [[nodiscard]]: Warns the caller at compile-time if the return value of a function is discarded (essential for state queries, validation checks, and resource allocations):
      • [[nodiscard]] auto IsShopStockLoaded( void ) const -> bool;
[[nodiscard]] auto ValidSpawnLocation( SI16 x, SI16 y, SI08 z, UI08 world, UI16 instance ) -> bool;

    Container & DFN Iteration

    Prefer range-based for loops over collections rather than legacy indexing or manual pointer stepping:

    // DFN section iteration
for( const auto *entry : npcSection->collection2() )
{
	if( entry->tag == DFNTAG_ID )
	{
		npcId = oldstrutil::value<UI16>( entry->cdata );
		break;
	}
}
  • Comments and Comment Blocks

    Function/Method Comment Blocks

    This Style Guide makes no differentiation between functions and methods for the purpose of comment blocks.

    • Comment blocks should be added for any new functions or methods added, should describe the purpose of the function/method and provide any extra context that is relevant for future maintainers of the code. For the sake of making the maintenance of comments more manageable, adopt a minimalistic approach where only relevant details are included:
      • //o-----------------------------------------------------------------------------------------------o
//| Function	-	CSocket::AddTrigWord()
//o-----------------------------------------------------------------------------------------------o
//| Purpose		-	Adds trigger word to list of trigger words detected in player's speech
//o-----------------------------------------------------------------------------------------------o
    • Getters/setters that have been grouped together should be commented together, where possible:
      • //o-----------------------------------------------------------------------------------------------o
//| Function	-	CSocket::TargetOK()
//o-----------------------------------------------------------------------------------------------o
//| Purpose		-	Gets/Sets socket property to indicate whether waiting for client target
//o-----------------------------------------------------------------------------------------------o
auto CSocket::TargetOK( void ) const -> bool
{
	return targetok;
}
auto CSocket::TargetOK( bool newValue ) -> void
{
	targetok = newValue;
}

    General Comments

    • Pay attention to grammar, spelling and punctuation, even in comments
    • Variables in general should have names that are descriptive enough that they'd not need comments, but if comments are needed - add them!
    • For global variables, try to always add a comment to explain what it's used for, and potentially why it needs to be a global variable
    • Don't remove comments added by other maintainers unless the comments in question are no longer relevant/accurate
    • If the use of magic numbers is necessary, add context for the magic number via comments
    • When deciding what to comment or not, try to think from the perspective of people maintaining the code after you're gone. Is it likely that someone will need some extra context to understand your code? Add a comment.
  • Console Logging

    Avoid direct calls to raw std::cout or std::cerr. Use UOX3's dedicated thread-safe console facility to format output, warnings, and errors with appropriate coloring and logging:

    Console.Log( "Starting spawner warmup..." );
Console.Warning( oldstrutil::format( "Invalid tile access: %u", tileNum ));
Console.Error( "Failed to allocate network worker buffer" );
  • Const
    • Make liberal use of const. Any member function that does not modify its object should be marked const:
      • auto CChar::GetHealth( void ) const -> SI16
{
	return health;
}
    • Any function parameter that references an object or string, but doesn't modify it, should be passed as a const reference:
      • auto AddMember( const std::string &name, const CItem *item ) -> bool;
    • For function parameters passed by value (like primitive integers or small enums), const has no effect on the caller and is not needed.
    • When declaring local read-only constants or pointers, follow these patterns:
      • const SI32 maxSearchRadius = 18;
const SI32 *ptrToConstInt = &maxSearchRadius; // pointer to const integer (const comes first)
  • Functions

    Write Short Functions

    • Write short functions, whenever possible. Sometimes it makes sense for a function to be a bit longer, but if the code in a function exceeds ~40 lines, start thinking about whether it could be broken up.
    • Short functions are easier to read, easier to test, easier to debug, and easier to modify.
  • Getters and Setters
    • Group getters and setters for class members together in pairs; put the getter for X next to the setter for X. Avoid spreading them out to different sections of a file. Grouping them up makes the code easier to read, maintain and debug:
      • auto CItem::GetType( void ) const -> ItemTypes
{
	return type;
}
auto CItem::SetType( ItemTypes newValue ) -> void
{
	type = newValue;
}
  • Memory Safety & Entity Lifecycle

    Always Validate Entity Pointers

    In UOX3, dynamic world entities (CChar*, CItem*, CMultiObj*) are managed by ObjectFactory and can be deleted, recycled, or decay at any point during gameplay. Never dereference raw entity pointers without checking their validity first:

    • Use ValidateObject( ptr ) on character, item, and multi pointers:
      • CChar *targChar = c->GetTarg();
if( !ValidateObject( targChar ))
	return;

targChar->SetMana( targChar->GetMana() - decrease );
    • Use VALIDATESOCKET( s ) or s != nullptr on client socket sessions:
      • void CSkills::Persecute( CSocket *s )
{
	VALIDATESOCKET( s );
	CChar *c = s->CurrcharObj();
	...
}

    Safe Entity Deletion

    • Never use raw C++ delete on CChar* or CItem* pointers.
    • Always invoke thing->Delete() so ObjectFactory safely removes the serial from the global registry, spatial world cells, script timers, and container references.
  • String Handling & String Utilities

    UOX3 provides a rich set of type-safe string manipulation helpers in StringUtility.hpp (namespace oldstrutil). Avoid legacy, unsafe C string functions (like sprintf, strcpy, strcat, or strtok) in favor of these utilities:

    • oldstrutil::format(): Safe string formatting similar to printf, returning a std::string:
      • std::string msg = oldstrutil::format( "Loaded %u items in region %i (World: %u)", itemCount, regionId, worldNum );
    • oldstrutil::sections(): Tokenizes and splits a string by a delimiter into a std::vector<std::string> (ideal for comma-separated or space-separated definitions):
      • auto coords = oldstrutil::sections( cdata, "," );
auto cmdTokens = oldstrutil::sections( speechText, " " );
    • oldstrutil::value<T>(): Converts strings to numeric types, with automatic support for decimal numbers and hexadecimal values (e.g. "0x1A4"):
      • UI16 itemId = oldstrutil::value<UI16>( entry->cdata );
SI32 amount = oldstrutil::value<SI32>( paramStr );
    • oldstrutil::trim(): Strips leading and trailing whitespace from a string:
      • std::string cleanName = oldstrutil::trim( rawName );
    • oldstrutil::upper() / oldstrutil::lower(): Returns uppercase or lowercase copies of a string:
      • if( oldstrutil::upper( commandName ) == "BANK" )
    • Standard String Literals: Use the s suffix (with using namespace std::string_literals;) to construct std::string literals directly:
      • auto greeting = "Welcome to UOX3!"s;
  • Variable Scope
    • Declare local variables when you need to use them, and not a moment sooner. The narrower the scope for a variable, and the closer it is declared to where it is actually used, the easier it becomes to read and understand the code for future code maintainers (or yourself a month from now).
    • If possible initialize variables as they are declared, instead of declaring and then assigning values to them separately, so whoever reads the code can see at a glance both the type and value the variable was initialized to.

      • Example: 

      // Not ideal
std::string myString;
myString = "Hello";

// Better
std::string myString = "Hello";

// Preferred
auto myString = "Hello"s; // note the 's' at the end
      • Exception: If the variable is an object, and it's used in a for-loop, declare it outside the for-loop so the constructor and destructor of the object doesn't get invoked multiple times as it loops.
  • Variable Types and Casting
    • Use the UOX3-defined type aliases like UI16, SI32, etc. for different integer types where possible, to increase readability and maintainability of the code. These are defined as follows: 
      using R32 = float;
using R64 = double;
using UI08 = std::uint8_t;	// 0 to 255
using SI08 = std::int8_t;	// -128 to 127
using UI16 = std::uint16_t;	// 0 to 65535
using SI16 = std::int16_t;	// -32768 to 32767
using UI32 = std::uint32_t;	// 0 to 4294967295
using SI32 = std::int32_t;	// -2147483648 to 2147483647
using UI64 = std::uint64_t;	// 0 to 18446744073709551615
using SI64 = std::int64_t;	// -9223372036854775808 to 9223372036854775807
    • Use C++-style casts, and avoid C-style casts. Example: 
      // Good - C++-style cast
static_cast<R32>( double_value )

// Avoid - C-style cast
( R32 )double_value
    • When in doubt about how large integer type is needed, prefer the larger type unless(i.e. UI64 over UI32, or SI32 over SI16)
  • Whitespace, Indentation and Braces

    Tabs vs Spaces

    For consistency with the rest of the code base, indent your code using tabs (size: 4), not spaces.

    Indentation

    • Vertical alignment can be done to increase readability in certain situations, like:
      • case CCP_FAME:			*vp = INT_TO_JSVAL( gPriv->GetFame() );					break;
case CCP_KARMA:			*vp = INT_TO_JSVAL( gPriv->GetKarma() );				break;
case CCP_ATTACK:		*vp = INT_TO_JSVAL( Combat->calcAtt( gPriv, true ));	break;
case CCP_CANATTACK:		*vp = BOOLEAN_TO_JSVAL( gPriv->GetCanAttack() );		break;
case CCP_BRKPEACE:		*vp = INT_TO_JSVAL( gPriv->GetBrkPeaceChance() );		break;
case CCP_HUNGER:		*vp = INT_TO_JSVAL( gPriv->GetHunger() );				break;
      pStream.ReserveSize( 44 );
pStream.WriteByte(   0, 0x1C );
pStream.WriteShort(  1, 44 );
pStream.WriteLong(   3, 0xFFFFFFFF );
pStream.WriteShort(  7, 0xFFFF );
pStream.WriteString( 14, "System", 6 );
pStream.WriteByte(   20, 0 );

    Whitespace Guidelines

    • Spaces inside parentheses
      • ( x, y, z )
    • Spaces after commas in list/function/method parameters
      • void MyFunction( std::string myString, SI32 myInt )
    • Spaces around operators
      • SI32 foo = x - 1;
bool bar = ( x <= 10 );
    • No spaces before parentheses in function or method declarations
      • bool myClass::MyMethod()
    • No spaces before parentheses in control statements
      • if( x == 1 )
for( SI32 i = 0; i < 10; ++i )
    • No spaces between multiple parentheses in control statements
      • if( foo || ( !bar ))
if(( x == y ) && ( z != x ))
    • No spaces inside angled or square brackets, except after comma, or between operators
      • [x, y, z]
static_cast<SI16>

    Braces

    • Braces ALWAYS on their own lines (Allman style)
      • if( something )
{
  ...
}

void myFunction( std::string myString )
{
}
    • Always use braces with if & else statements, even for one liners, to prevent easy mistakes by future maintainers
      • if( something )
{
	// one liner
}
    • Exception to the previous point: Braces can be skipped for one-liners that are intended to return early, continue/break a loop, etc. In those cases, try to leave an empty line after the early return/continue/break and the rest of the code in the function/method in question
      • bool cScript::OnCreate( CBaseObject *thingCreated, bool dfnCreated )
{
	if( !ValidateObject( thingCreated ))
		return false;

	std::string functionName = "onCreateDFN";
	...
}
      for( auto &MapArea : MapRegion->PopulateList( this ))
{
	if( MapArea == nullptr )
		continue;

	// First remove nearby characters from sight
	...
}

  • JavaScript (JSE) Style Guide

  • ES6+ Language Syntax (SpiderMonkey 115)

    UOX3 embeds a SpiderMonkey 115 JavaScript engine. All scripts support and should utilize standard ES6+ language features:

    • Prefer const and let over var. Use const for immutable values and references, and let for variables that change or loop iterators:
      • // Preferred
const targetLocation = pUser.targetLoc;
let totalGold = 0;

// Avoid
var myGold = 0;
    • Template Literals: While in-game player messages should rely on GetDictionaryEntry() for localization, backtick string interpolation (${value}) is supported in SpiderMonkey 115 and can be used for constructing internal debug messages and logs:
      • Console.Log( `Spawned ${spawnCount} creatures for region ${regionName}` );
  • General Script Formatting

    JavaScript scripts in UOX3 follow the same fundamental formatting and casing principles as C++ code (see Basic Style Guide and Whitespace & Braces):

    • Indent using tabs (tab size: 4), not spaces.
    • Place braces on their own lines (Allman style).
    • Leave spaces inside parentheses: if( pUser.isChar ), function onUse( pUser, iUsed ).
    • Spaces around arithmetic, comparison, and assignment operators: pUser.mana -= 10;
    • Function & Variable Casing:
      • Script functions and methods must use PascalCase: function CalculateReward( pUser, tier ), function GiveBonusGold( pUser )
      • Engine Event triggers must use camelCase: function onUse( pUser, iUsed ), function onAttack( pAttacker, pDefender ), function onSpeech( pSpeech, pSpeaker, text ), function onCollide( pUser, iTile ), function onDeath( pVictim, pKiller )
      • Variables, properties, and parameters must use camelCase: const goldBonus = 500;
  • Object Prefixes & Safety Guards

    Standard Script Object Prefixes

    To keep scripts intuitive and self-documenting, use standard prefixes for objects passed to event triggers:

    • pUser, pTarget, pAttacker, pDefender, pSpeaker (Characters / Mobiles)
    • iUsed, iWorn, iCrafted, iTarget (Items)
    • iSocket, tSock (Client Sockets)
    • tGump (Gump dialogs)

    Safe Guard Checks

    Always guard event triggers with early returns to ensure objects exist before accessing properties or calling methods:

    function onUse( pUser, iUsed )
{
	if( !pUser || !iUsed || !pUser.isChar )
		return false;

	if( !pUser.InRange( iUsed, 3 ))
	{
		pUser.SysMessage( "You are too far away." );
		return false;
	}

	return true;
}
  • TypeScript Definitions & Type Checking

    File Header Directives

    To enable autocompletion, hover tooltips, and static type validation in code editors (like VSCode), JavaScript files in UOX3 should begin with a relative reference path directive to definitions.d.ts and the // @ts-check pragma:

    /// <reference path="../definitions.d.ts" />
// @ts-check

    Ensure the relative path to definitions.d.ts matches the folder depth of the script (e.g. ../definitions.d.ts for scripts in subdirectories or ../../definitions.d.ts for nested subdirectories).

    Function Type Annotations (JSDoc)

    Functions in scripts should include JSDoc @type annotations specifying parameter types and return values. This provides instant type-checking, property autocompletion, and catches invalid method calls:

    /** @type { ( user: Character, iUsing: Item ) => boolean } */
function onUseChecked( pUser, iUsed )
{
	...
}

/** @type { ( socket: Socket, cmdString: string ) => void } */
function command_SKIN( socket, cmdString )
{
	...
}

/** @type { ( attacker: Character, defender: Character ) => number } */
function CalculateCombatDamage( pAttacker, pDefender )
{
	...
}

    Common types defined in definitions.d.ts include Character, Item, Socket, BaseObject, GumpData, string, number, boolean, and union types like Character | Item | null.

    Refer to data/js/definitions.d.ts for the full list of engine object classes, type definitions, and event signatures, or consult the UOX3 JavaScript Engine Documentation (jsdocs.html) for detailed method and property documentation.

  • PR & Changelog Guidelines

  • Automated Changelog Workflow

    This guide outlines how to format changelog entries in Pull Request (PR) descriptions on GitHub so that they are automatically parsed, formatted, and prepended to source/Changelog.txt when a PR is merged.

    • The automated workflow only extracts lines starting with a dash (- ).
    • Any other lines (Markdown headers, discussions, testing notes, screenshots) are automatically ignored.
    • Top-level entries (- [TAG]) are formatted with 4 leading spaces in Changelog.txt.
    • Indented sub-points ( - ) are formatted with 8 leading spaces in Changelog.txt.
    PR Description Format:
- [TAG] Main entry description...
  - Sub-item, syntax line, or usage example
  - Another sub-item line

Resulting Changelog.txt Output:
DD/MM/YYYY - Author (#PR_NUMBER)
    [TAG] Main entry description...
        Sub-item, syntax line, or usage example
        Another sub-item line
  • Category Tags Reference

    Every top-level changelog entry must begin with one of the primary tags:

    • - [ADD] - New Additions: New features, gameplay systems, JS methods/properties/events, global functions, DFN tags, INI settings, GM commands, item/NPC definitions, or CI workflows.
    • - [UPD] - Updates & Enhancements: Behavioral changes, expansions to existing function signatures, balance adjustments, migrations, refactoring, dependency upgrades, or documentation.
    • - [FIX] - Bug Fixes & Crash Resolutions: Bug fixes, crash resolutions, logic corrections, packet errors, movement desyncs, missing null/socket checks, or typos.
    • - [MISC] - Optional Catch-All: Fallback tag for general housekeeping, minor cleanups, or miscellaneous adjustments that do not fit the primary categories.
  • Formatting & Content Rules

    Avoid Vague One-Liners & Internal Code Churn

    A good changelog entry provides high-value functional specifics (what changed, why it changed, and how to use it) rather than vague one-liners or raw diff churn.

    • BAD: - [FIX] Fixed combat bug
    • GOOD: - [FIX] Fixed an issue in combat where defender's poison resistance was ignored when calculating poison strike damage
    • BAD: - [UPD] Updated spells.js
    • GOOD: - [UPD] Updated Earthquake and Chain Lightning spells (js/magic/spells.js) to check for safe zone regions before applying area damage
    • BAD: - [ADD] Added new properties
    • GOOD: - [ADD] Added new Character JS property .damageIncrease to track item-based damage bonuses
    • BAD: - [UPD] Changed variable x on line 42 from UI16 to UI32 in combat.cpp
    • GOOD: - [UPD] Expanded combat damage calculations to 32-bit integers to prevent numerical overflow when weapon damage exceeds 65,535

    Clear Action & Behavior

    • Entries typically start with an action word ("Added...", "Fixed...", "Updated...") or directly name the affected system/entity ("In-game time is now tracked...", "Dead bonded pets are now flagged...").
    • Describe how the feature works in the game now: "...allowing players to walk through them", "...triggers when...", "...is now tracked in 24h format".

    Common Sentence Patterns

    • Fixes: Fixed an issue where [what went wrong] (path/to/script.js)
    • Additions: Added new [feature/system/command] that [does what]
    • Updates: Updated [system/function] to [do what]

    Concise Phrasing & Single-Line Preference

    • Aim for concise, single-line entries per logical change where the main point suffices.
    • Avoid storytelling, hyperbole, technical deep-dives, and overly verbose sentences; stick to simple facts with neutral language.
    • Drop redundant helper words when context is already clear (prefer "Gets percentage assigned to damageType" over "Returns the percentage assigned to the specified damageType").

    Sub-Points & Multi-Line Entries

    • Use sub-points ( - ) when providing function/method syntax overloads, multi-line INI settings, DFN tags, grouped property lists, examples, or distinct configuration options that need a line of their own.
    • Avoid breaking general narrative explanations or technical background into unnecessary sub-points when a single top-level entry is sufficient.

    Standard Naming & Identifiers

    • JS properties and methods start with a dot: .vendorGoldHeld, .AddMember() (specify object type like Character/Item/Socket, and note if read-only).
    • In-game commands start with an apostrophe: 'showspawnregions, 'settime, 'storm.
    • Script and definition paths go in parentheses: (js/skill/healing.js).
    • C++ class and function names may be mentioned when relevant (e.g. CSkills::UpdateSkillLevel), but only mention C++ source filenames when relevant (files added, removed, moved, or renamed).
    • Multi-line DFN tags, INI settings, and full function signatures go on indented sub-bullets with // comments explaining parameters or defaults.
    • Use standard Ultima Online terms: paperdoll, visrange, gump, cliloc, rubberbanding, bonded pets, young status.
  • Template & Examples

    PR Description Template

    - [ADD] Description of new feature, system, command, or JS API
  - Optional syntax, parameter description, code example, or configuration option
- [UPD] Description of updated gameplay mechanics, modified function signatures, or refactoring
  - Optional parameter list, overload syntax, or configuration details
- [FIX] Description of fixed bug/crash, specifying root cause, symptoms, and affected files (path/to/file.ext)
- [MISC] Optional catch-all for minor housekeeping or general adjustments

    Concrete Examples

    - [ADD] Added 'storm GM command (js/commands/custom/storm.js) to temporarily override weather in current region and force a storm on next weather update

- [ADD] Added new Item DFN tag to allow definition of custom container gumps:
  - gumptype=gumpid,xMin,xMax,yMin,yMax,z // Custom bounds for random placement (optional)

- [ADD] Added new Multi JS Methods for managing player vendors in player houses:
  - .AddVendor( playerVendor ) // Register player vendor with multi
  - .RemoveVendor( playerVendor ) // Unregister player vendor from multi

- [ADD] Introduction of speedhack anti-cheat system governed by new settings in [anticheat] section of uox.ini:
  - SPEEDHACKDETECTION=1 // Enables/disables speedhack detection system
  - SPEEDHACKTHROTTLEPENALTY=2000 // Movement throttle penalty (in ms) applied when speedhack is detected
  - SPEEDHACKMAXDEBT=350 // Max movement debt (in ms) player can accumulate before throttling occurs
  - SPEEDHACKMAXDEBTAVG=0.5 // Max average debt as factor of SPEEDHACKMAXDEBT before triggering warning log
  - SPEEDHACKMAXCREDIT=-75 // Movement credit buffer (in ms) for regular players against jitter/lag
  - SPEEDHACKGRACETHRESHOLD=2000 // Grace threshold to handle large server/network lag spikes

- [ADD] Added new Socket JS properties for movement tracking:
  - .moveDebt // Accumulated time debt in ms (early arrival = potential speeding, late = lag)
  - .moveDebtAvg // Accumulated time debt in ms, averaged over at least 100 samples
  - .moveBurstAllowance // Number of upcoming movement steps processed without incurring penalty
  - .nextMoveTime // Timestamp in ms for when next valid movement packet is expected to arrive

- [UPD] Extended JS Function DoMovingEffect to support optional stationary effect flag. Updated syntax:
  - DoMovingEffect( srcObject, trgObject, effect, speed, loop, explode, [hue], [renderMode], [stationaryFX] )
  - DoMovingEffect( srcObject, targX, targY, targZ, effect, speed, loop, explode, [hue], [renderMode], [stationaryFX] )
  - DoMovingEffect( srcX, srcY, srcZ, targX, targY, targZ, effect, speed, loop, explode, [hue], [renderMode], [stationaryFX] )

- [UPD] Updated spellbook lookup (via IsSpellBook() item function), casting, display, scroll insertion and spell packet generation to rely on the range defined by SPELLBOOKDATA, while preserving support for traditional type 9 spellbooks

- [FIX] Fixed house decay timers not getting reset properly upon door usage (js/item/doors.js) and when grandfathered state is enabled for house (js/server/house/house.js)

- [FIX] Fixed server crash in CGump::AddXMFHTMLTok caused by empty cliloc argument arrays sent from newer clients

    • Sub-points and syntax lines are indented with two spaces: -
    • Clearly states what changed, was added, fixed, or updated
    • Fixes explain what went wrong and what was fixed ("Fixed an issue where X would Y")
    • JS properties name the object type (Character, Item, Socket) and note if read-only
    • New DFN tags, INI settings, and functions include syntax and // comments on sub-bullets
    • Script and definition fixes mention the file path in parentheses: (js/path/to/file.js)
